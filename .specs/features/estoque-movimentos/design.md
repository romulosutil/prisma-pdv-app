# Estoque derivado do registro de movimentos

Produto conserva `estoque` como saldo inicial. `ajustesEstoque` é uma lista append-only de {id, quantidadeMilesimos, criadoEm, motivo}. `estoqueAtivo=false` oculta o saldo sem apagar a base. Item de venda recebe `controlaEstoque` no commit da conclusão. Ausência significa histórico anterior, sem movimento. Cada item marcado contribui com -quantidade; cancelamento comercial neutraliza essa baixa. A venda e seus itens já são gravados atomicamente com outbox no Android, portanto não haverá segunda escrita de saldo que possa divergir.

O saldo exibido é base + soma de ajustes - soma de itens marcados em vendas concluídas. Histórico usa os mesmos registros e mostra baixa e reposição separadas. Nenhum saldo projetado vai para a outbox de produto. ProdutosRepo recebe consulta de vendas; os hooks assinam as duas fontes. Alterar o campo de estoque cria uma diferença, sem substituir base. O formulário transmite o saldo observado na abertura somente como argumento local, para que a diferença não absorva uma venda concorrente. Campo intocado é omitido pelo formulário, preservando venda concorrente. Campo vazio marca inativo; reativação calcula diferença sobre o saldo contábil preservado. Unidade de base já controlada é imutável.

API adiciona JSONB de ajustes, boolean ativo e boolean nullable nos itens por migração Drizzle aditiva. União de ajustes ocorre mesmo quando os metadados recebidos perderam no LWW. Mesmo ID com outro conteúdo é rejeitado. O servidor conserva ajustes omitidos pelo cliente. Base fica congelada ao adotar o novo contrato ou classificar uma venda controlada. Escritas de estoque continuam sujeitas ao recurso do plano. Vendas antigas não são alteradas; novos itens sem marcador (cliente antigo) são classificados pela configuração atual do produto da mesma loja. Marcador fornecido e referências controladas são validados; cancelamento conserva marcador salvo. A conta/loja já tem lock transacional no push.

Compatibilidade: API é atualizada antes do app. Apps antigos não projetam saldo e devem ser atualizados antes de depender do controle de estoque. A migração não reconta vendas; novos campos opcionais mantêm payloads anteriores legíveis. Cancelamentos de histórico sem marcador não repõem saldo presumido. O novo app depende da API que preserva os novos campos.

SQLite não exige nova tabela: os novos campos ficam nos JSONs versionados existentes. Navegador usa o mesmo envelope. A projeção do estoque passa a refletir somente vendas confirmadas localmente, incluindo pendentes de envio. Pull/ACK conserva IDs de vendas e itens e não cria movimentos duplicados. Falha e reinício conservam o mesmo registro financeiro. Quantidades são inteiros seguros em milésimos, somados com BigInt e verificados antes de converter.
