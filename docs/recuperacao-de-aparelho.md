# Identidade e recuperação de aparelho

A instalação guarda um UUID global público. Cada conta usa um aparelho lógico próprio, pois a API vincula esse ID a uma única conta. O vínculo por e-mail normalizado é persistido antes de cadastro/login e reutilizado nos logins seguintes; alternar A→B→A não cria um terceiro aparelho. A primeira conta e a sessão legada preservam seu ID autorizado. A instalação global não muda quando o aparelho lógico muda de conta.

Uma reinstalação pode apagar identidade, credencial e dados locais. Não reinstalar nem apagar vendas para contornar limite ou falha de acesso. O dono encontra consulta e revogação em Ajustes → Conta e aparelhos, na versão conectada. Revogar encerra as sessões no servidor, conserva o histórico e permite autenticar um aparelho substituto no limite liberado. O aparelho revogado não se reativa silenciosamente por login. A restauração completa de dados confirmados depende de P0-02, ainda pendente; operações nunca sincronizadas exigem preservar o aparelho de origem e o procedimento de recuperação.

O token nativo é referenciado por UUID e guardado no SecureStore; metadata comum conserva somente identidade/perfil e referências sem segredos. A migração verifica a escrita no cofre antes de sanitizar o legado. Credencial ausente exige autenticação novamente e preserva a identidade financeira; cofre indisponível ou dados inválidos produzem erro recuperável sem gerar outro ID/token. A versão browser é demonstrativa.

Login em outra conta é bloqueado antes de gerar novo vínculo ou chamar o backend quando houver pendências. O bloqueio de gravação se mantém durante a troca. Até existir confirmação de sincronização em P0-02, registros financeiros locais são tratados conservadoramente como pendentes. Entrar novamente na mesma conta recupera o checkout, inclusive parcelas já recebidas. Perfil legado ausente exige recuperar primeiro a conta original com seu aparelho autorizado; só depois é permitida outra associação.

Logout diferencia revogação confirmada no servidor de saída somente local quando não há conexão. Em falha de metadata ao retirar um token rejeitado, o app nega acesso em memória e tenta retirar apenas esse token do cofre. Se ambos os armazenamentos falharem, não há garantia de exclusão durável; preserve os registros e recupere o acesso. O reset de desenvolvimento também tem uma janela entre base e cofre, podendo deixar uma credencial órfã sem referência se houver interrupção e falhas combinadas. Esse reset não é um procedimento de produção.

Testes com API real em processo (PGlite), SQLite local e cofre simulado verificaram perfil, expiração, revogação e troca entre duas contas. Esses testes não comprovam SecureStore físico, restauração, scanner ou navegação em Android. Entrega de código por e-mail e homologação externa continuam pendentes.
